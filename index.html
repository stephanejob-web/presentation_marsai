Choix Technologique

Pourquoi TypeScript · pas JavaScript ?

🔷

6 devs · 6 styles

Sans types, chacun passe des données différentes aux fonctions. TypeScript impose un contrat commun. Le compilateur détecte les incohérences avant l'exécution.

🛡️

Erreurs à la compilation

Un bug TypeScript = erreur immédiate dans l'éditeur. Un bug JavaScript = erreur en production devant l'utilisateur.

⚡

Refactoring sûr

Renommer une prop, changer une interface → le compilateur liste tous les endroits à corriger. Impossible d'en oublier un.

JavaScript ← ce qu'on aurait eu
// Aucun contrat — chacun passe ce qu'il veut function scoreFilm(film, note) { return film.titre + " : " + note.valeur; } // Dylan appelle : scoreFilm({ title: "..." }, 8) // → undefined au runtime. Bug silencieux.
TypeScript ← ce qu'on a choisi
// Interface partagée — tout le monde voit le contrat interface Film { titre: string; id: number; } interface Note { valeur: number; // 0–10 juryId: number; } function scoreFilm(film: Film, note: Note): string { return `${film.titre} : ${note.valeur}/10`; } // Dylan appelle : scoreFilm({ title: "..." }, 8) // ✖ Erreur immédiate : 'title' n'existe pas sur Film // ✖ Erreur immédiate : number n'est pas Note
Exemple réel — useState toujours typé
// ❌ JavaScript / TS sans strict const [films, setFilms] = useState([]); const [error, setError] = useState(null);
// ✅ TypeScript strict — utilisé dans le projet const [films, setFilms] = useState<Film[]>([]); const [error, setError] = useState<string | null>(null); const [isLoading, setLoad] = useState<boolean>(false);
TypeScript = filet de sécurité collectif. Sur un projet à 6, un type manquant = un bug potentiel pour toute l'équipe.
Problème Réel · Solution Progressive

Mac · Linux · Windows — Zéro compatibilité par défaut

💥

Le problème concret

Stéphane sur macOS / Linux
Collaborateurs sur Windows

● Fins de ligne LF vs CRLF → diffs Git pollués
● Chemins de fichiers / vs \ → erreurs au build
● Versions Node différentes → comportements divergents
● "Ça marche chez moi" → bloquant en intégration

🔷

Étape 1 — TypeScript strict

Premier rempart contre les divergences.

● Types explicites = même contrat sur tous les OS
● Le compilateur détecte les erreurs avant l'exécution
● strict · noUnusedLocals · noUnusedParameters
● Un seul tsconfig.json partagé dans le repo

🎨

Étape 2 — Prettier "endOfLine": "lf"

Résout les fins de ligne CRLF/LF.

● Force LF sur tous les OS
● Git ne voit plus de diffs parasites
● Prettier reformate automatiquement au pre-push

🐳

Étape 3 — Docker Compose · La solution définitive

Un seul docker-compose.yml → même environnement sur Mac, Linux et Windows sans exception.
Node version fixée · MySQL version fixée · variables d'env uniformes · réseau interne isolé.

docker-compose.yml
services: frontend: build: Dockerfile.frontend ports: ["5173:5173"] backend: build: Dockerfile.backend ports: ["5500:5500"] db: image: mysql:8 environment: MYSQL_ROOT_PASSWORD: ****
✅

Résultat

docker compose up
et c'est identique
sur tous les OS

Conventions Git

CommitLint — Chaque commit raconte une histoire

commitlint.config.js
module.exports = { extends: ['@commitlint/config-conventional'] };
# .husky/commit-msg npx --no -- commitlint --edit $1
Hook commit-msg s'exécute à chaque commit.
Format invalide = commit refusé instantanément.
Vrais commits du projet
✔ feat(jury): ajout qr code apk android ✔ fix(jury): migration localStorage classic→rapide ✔ style(jury): prettier fix sur mobile app view ✔ fix(docker): correction INSERT jury dans init.sql ✔ feat(home): mise en avant lightchurch sponsor ✔ feat(juryresponsive): touchscreen support mobile
# ✖ Automatiquement rejetés ✖ "ajout truc" → message trop court ✖ "fix" → sans scope ✖ "WIP en cours" → type invalide ✖ "corrections diverses" → pas de type

C'est quoi ?

Une convention de nommage stricte (type: description) pour standardiser les messages de l'équipe.

Pourquoi ?

Facilite la lecture de l'historique, permet l'automatisation des versions et des CHANGELOG.

IA Augmentée · Utilisée intelligemment

Nous avons dirigé l'IA — elle ne nous a pas remplacés

🧠

L'IA = un junior très rapide

Elle écrit vite. Mais sans cadre, elle invente ses propres conventions, duplique du code, ignore les patterns existants.

Sans contrôle = chaos garanti sur 6 devs.

🎯

Notre approche

On lui donne le contexte avant qu'elle code.
On contrôle après qu'elle a codé.
On valide chaque PR humainement.

📄 conventions.md — lu avant chaque session

Les règles qu'on lui impose

extrait du prompt
# Ce que l'IA DOIT faire avant d'écrire 1. Lire l'arborescence — ne rien créer qui existe déjà 2. Utiliser services/api.ts — jamais fetch() direct 3. TypeScript strict — zéro any, types explicites 4. Écrire les tests unitaires avec le composant
# Ce qui est interdit sans exception any · console.log · @ts-ignore · inline style créer un 2e Button, un 2e apiFetch, un 2e useLoading

Claude · Copilot · chaque outil lit ce fichier. Résultat : code identique en style et structure quel que soit le dev qui a utilisé l'IA.

📄 review.md — après chaque feature

On la fait se relire elle-même

Une fois la feature terminée, l'IA change de rôle : elle devient reviewer senior et relit son propre code avec un œil critique.

1

Lance npm run check

Diagnostic complet : format · lint · types · tests

2

Corrige ESLint

Jamais de eslint-disable — corriger le code

3

Détecte les duplications

Extrait composant ou hook si besoin

4

Boucle jusqu'au vert

npm run check → corriger → répéter

L'IA est un outil sous contrôle · pas un auteur autonome.
Chaque ligne générée est relue · testée · validée par un humain avant d'atteindre la PR.
Review Automatisée

CodeRabbit — Reviewer IA sur chaque PR

🤖

Déclenchement automatique

Chaque PR vers develop ou main déclenche CodeRabbit. Profil : assertive. Langue : français. Aucune action manuelle requise.

🔍

Ce qu'il analyse

Bugs potentiels · failles sécurité
Performance · duplication
TypeScript strict · tests manquants
Correspondance avec la maquette HTML

.coderabbit.yaml — instructions par chemin
path_instructions: - path: "frontend/**/*.tsx" instructions: | - Composant fonctionnel, jamais de classe - TypeScript strict : pas de any - Vérifier présence des tests unitaires - Réutiliser composants existants dans /ui - Correspondance avec la maquette HTML
- path: "backend/**/*.ts" instructions: | - Sécurité : pas d'injection SQL - Sanitizer tous les inputs utilisateur - Gestion d'erreur sur chaque route - Routes protégées si nécessaire
Workflow complet : feature branch → npm run check → PR → CodeRabbit → review humaine → merge.
Deux niveaux de review pour chaque ligne de code avant merge.

AWS S3 tombe · MinIO prend le relai

🔥

Le problème

Le bucket AWS S3 ne répond plus.

● Upload des vidéos de films : HS
● Lecture des fichiers stockés : HS
● Tout le module jury dépend du stockage

→

La solution : MinIO

MinIO = S3-compatible, auto-hébergé, tourne dans Docker.

● API 100% identique à AWS S3
● Aucune modification du code applicatif
● Ajouté au docker-compose.yml existant
● Fonctionnel en quelques heures

docker-compose.yml — ajout MinIO
minio: image: minio/minio ports: ["9000:9000", "9001:9001"] command: server /data --console-address ":9001" environment: MINIO_ROOT_USER: minioadmin MINIO_ROOT_PASSWORD: **** volumes: [minio_data:/data]
